# Deterministic 3D Vehicle Hull Physics — P2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every vehicle ride the existing height field with deterministic suspension and a gameplay-authoritative 3D pose.

**Architecture:** Keep the existing driver, route, crew and firing decisions, but make them produce drive requests. A ten-substep rigid-body solver owns the resulting position and orientation; combat, navigation and the renderer consume that pose. Ground contact has a replaceable probe for P3, while P2 retains existing terrain and vehicle blocking.

**Tech Stack:** TypeScript, Vitest, existing `dmath`, existing three.js renderer and Blender mesh exporter; no new runtime dependency.

**Spec:** `docs/superpowers/specs/2026-10-07-3d-vehicle-physics-design.md` (approved conversation; its written status predates approval).

## Global Constraints

- “The sim owns every vehicle's 3D pose: position, height, heading, pitch and roll. The renderer only draws it.”
- “Steering stays as it is.” Preserve turn rates, turning radius, short halts, give-way, reversing, wire, crew and damage decisions.
- “Each SIM_DT (0.1 s) tick runs 10 sub-steps of 10 ms, using semi-implicit Euler, and the quaternion is renormalised every sub-step.”
- “Only IEEE + − × ÷ sqrt and dm.*. No Math.* transcendentals and no **”. Existing integer/clamp helpers remain legal.
- “Vehicle.body goes into hashState.” Hash exact float64 bits, including timers and flags that influence future ticks.
- “The target is under 0.5 ms per tick for 40 vehicles in Node.” Measure awake and asleep cases separately.
- “Vehicles never drive through each other” and “Buildings as physics objects; they stay impassable, as now.”
- No P3 obstacle objects, P4 blast/mine impulses, P5 hull pushing, terrain deformation beyond the existing height field, or backlog 055. Backlog 054 may subsequently produce height changes through the wake interface defined here.
- Keep the user’s running server/browser untouched; preserve untracked `ref/`. Do not change the current deterministic baseline until a reviewed, explained P2 baseline is available.
- This document is a proposal for human review. Do not implement it before that review; the writing-plans skill explicitly requires this gate.

## Review Focus

1. Reverse, creep, give-way, frozen turret and early-return branches must step physics exactly once, without applying mines/crushing/runover at a speculative position (Tasks 5A–5B).
2. Sleep followed by terrain edits, deploy repositioning or desync rebuild must not leave stale cached height/pose or create a second source of movement truth (Tasks 2, 4, 5, 11).
3. A tipped or airborne vehicle must not gain drive force from unloaded contacts, sink through the terrain on its roof, fire while rocking, or recover from permanent overturn (Tasks 3, 6, 7).
4. A turret traversed sideways on a pitched hull, a casemate and a blown-off turret must use the correct distinct coordinate frames (Tasks 7–9).
5. Map edges, high feature steps and terrain/hull blockers must remain finite and deterministic, including when one tick could cross more than one tile (Tasks 2, 5, 10).

## Decisions and file boundaries

Sim world coordinates are right-handed: x east, y south, z up, all metres. Body-local axes are x right, y rear, z up; forward is `(0,-1,0)`. Positive rotation around z gives the existing clockwise-from-north heading. `Vehicle.pos` remains tile coordinates, derived by dividing x/y by `TILE_M`. Quaternions are local-to-world. Body position is the centre of gravity (CG); model origin is a separate offset, never assumed equal to CG.

Create `src/sim/hullMath.ts` (small vector/quaternion operations), `hullGround.ts` (height-field probe), `hullPhysics.ts` (contact/integration/sleep), `hullGameplay.ts` (rocking/overturn consequences), `hullAim.ts` (shared gun/hit frames), and `src/data/vehiclePhysics.ts` (explicit tuning and provenance). Do not grow `vehicle.ts` into the solver. Modify the current owners of movement, damage, path, state hashing, spawning and rendering.

Use structural types in `src/shared/types.ts`:

```ts
export interface Vec3 { x: number; y: number; z: number }
export interface HullQuat { x: number; y: number; z: number; w: number }
export interface HullBody {
  position: Vec3; orientation: HullQuat;
  velocity: Vec3; angularVelocity: Vec3; // world frame, m/s and rad/s
  suspensionTravel: number[]; // compression metres, deterministic contact order
  asleep: boolean; hungUp: boolean; overturned: boolean;
  quietS: number; tippedS: number; hungS: number;
  rockPhaseS: number; rockTries: number;
  groundVersion: number;
}
export interface HullDrive { speedMs: number; yawRateRadS: number; brake: boolean }
export interface HullGroundSample { heightM: number; normal: Vec3 }
export type HullGroundProbe = (xM: number, yM: number) => HullGroundSample;
export interface SuspensionDef { springKNm: number; damping: number; travelM: number }
```

`Vehicle.body?: HullBody`, `Vehicle.gunElevationRad?: number`. Extend `VehicleDef` with optional `massT`, `hullHeightM`, `cgHeightM`, `suspension`, `driveKind: 'tracked'|'halftrack'|'wheeled'`, `slopeComfortDeg`, `slopeTipDeg`, `gunDepressionDeg`, `gunElevationDeg`; make these required in `HullParams`, the normalized return of `hullParams(def: VehicleDef)`. `armor.belly?: number` defaults to top. Explicit driveKind matters: current `kind: 'halftrack'` includes Kübelwagen and BM-13; Kettenkrad has a single front wheel. Do not infer their wheel layouts solely from kind.

Scalar `clamp` and `wrapAngle` come from `src/shared/math.ts`; `dm` is `import * as dm from '@/shared/dmath'`. All code snippets belong to their named file, with the types/imports specified in that task.

Initial numeric tuning is an explicit gameplay assumption, not a historical claim: damping is a dimensionless critical-damping ratio 0.9; travel 0.28 m tracked / 0.22 m wheeled; equilibrium compression 0.35 of travel; contact friction coefficient 0.8 multiplied by the existing going factor; drive velocity controller time constant 0.4 s. Derive each spring stiffness from `massKg*9.81/(loadedContactCount*0.35*travelM)/1000`; horn points do not count as resting supports. Use dimensions from current definitions/models. Record each mass source or mark the value “estimated for simulation”. A safe unverified fallback is density 2 t/m³ × length × width × hullHeight for armored vehicles, 0.3 for unarmored; it is a fallback, not evidence. For acceptance-fixture calibration use explicit **provisional** T-34/76 26 t, KV-1 45 t, SdKfz 251 8 t, then verify primary references before labelling them historical. Do not silently publish historical certainty.

The 35° side-slope acceptance requires a narrow/high-CG halftrack and a stable KV-1, not a mass-only tipping rule. Initial effective CG assumptions: SdKfz 251 1.45 m, KV-1 1.10 m. Derive tipping angle from actual support width and CG (`dm.atan2(halfSupportWidth,cgHeightM)`); calibrate suspension/contact geometry against that test. Comfort defaults 12° tracked / 10° wheeled; limits are documented tuning, not historical climbing claims. Gun-limit fallback is depression 5°, elevation 20°; catalog exceptions need evidence before being described as historical.
